# Bug修复记录

本文记录已经确认的问题、根因和修复方式，便于维护者避免回归。

## （未发布）：退出应用后，后端 sidecar 进程没有一起退出

### 现象

正常退出「知档」（Dock 图标右键退出，或 Cmd+Q）之后，内嵌的 Node 后端（`zhidang-server` sidecar）并没有跟着一起结束，而是变成孤儿进程（`ppid` 被系统重新指给 `launchd`），继续占用它绑定的端口（login 版 4317 / key 版 4318）。两个 edition 都受影响，因为都走同一份 `spawn_backend_sidecar`。

实际影响：如果用户退出后重新打开应用（不管是同一个 edition 还是另一个），新实例的窗口有可能直接连上这个还在运行的旧 sidecar，而不是自己刚启动的那个——旧进程不会报错，只是悄悄提供上一次会话的状态/缓存数据，不会有任何提示。开发/测试时尤其容易被这个假象误导；对最终用户来说，意味着重新打开的应用可能在和一个上一次会话遗留下来的后端说话。

### 根因

`spawn_backend_sidecar`（`src-tauri/src/lib.rs`）通过 `tauri_plugin_shell` 启动 sidecar 时，把 `sidecar.spawn()` 返回的 `CommandChild` 直接绑定到 `_child` 丢弃掉了——没有任何地方持有这个句柄，也就没有任何地方能在退出时调用它的 `kill()`。`tauri_plugin_shell` 启动的子进程不会因为父进程（Tauri App）退出就自动被系统终止：它是完全独立的进程，需要显式 `kill()` 才会退出。

另外验证时发现一个不直观的坑：最初尝试把 kill 挂在 `RunEvent::ExitRequested` 上（Tauri 官方示例里 sidecar 清理常用的钩子），但给每个 `RunEvent` 加日志、用真实签名+公证过的 `.app`、通过 Dock 退出和 `osascript ... to quit` 实测后发现，正常的 macOS 退出流程根本不会发出 `ExitRequested`——事件循环是从一串 `MainEventsCleared` 直接跳到 `Exit`，`ExitRequested` 从未触发。挂在 `ExitRequested` 上的清理逻辑在这个最常见的退出路径下会静默失效。

### 修复

新增一个受 Tauri 状态管理的 `SidecarProcess(Mutex<Option<CommandChild>>)`，`spawn_backend_sidecar` 把 `spawn()` 返回的 `CommandChild` 存进去而不是丢弃；`run()` 里把 `.run(context)` 拆成 `.build(context)` + `app.run(callback)`，在 callback 里匹配 `RunEvent::Exit`（不是 `ExitRequested`）调用 `kill_backend_sidecar`，取出并 `kill()` 这个句柄。两个 edition 的 `run()` 都改了。

### 验证

用 `npx tauri build --bundles app`（login）和 `npx tauri build --config src-tauri/tauri.key.conf.json -f key --bundles app`（key）各打出一个真实签名+公证的 `.app`，分别用 `scripts/verify-sidecar-exit.sh <path-to-.app>` 自动验证：启动、确认 sidecar 进程存在、通过 `osascript ... to quit` 正常退出、确认 sidecar 进程确实一起消失了——两个 edition 都通过。

### 防回归要求

- `tauri_plugin_shell` 起的 sidecar 子进程生命周期不跟父进程绑定，任何新增的 sidecar 必须显式持有它的 `CommandChild` 并在退出路径里 `kill()`，不能假设"父进程没了子进程也会没"；
- 排查 Tauri 的退出/生命周期问题时不要凭对 `RunEvent` 变体名字的直觉猜测该挂哪个钩子（`ExitRequested` 听起来最像，但常见的 macOS 退出路径根本不发它）——给 `RunEvent` 加日志、在真机上用真实退出方式（Dock 退出/Cmd+Q/`osascript`，不只是关窗口）实测一遍事件顺序；
- 发布前用 `scripts/verify-sidecar-exit.sh` 走一遍两个 edition，见 `docs/RELEASE_CHECKLIST.md`。

## 1.2.0：登录版图标圆角调"圆"之后，macOS 给整个图标套了一层灰框

### 现象

尝试把登录版图标的圆角改得更接近苹果 squircle 曲线（用了一个更激进的曲率）后，Finder/Dock 里的图标显示出问题：图标整体缩小了一圈，外面多出一层系统自己画的浅灰色圆角方框，跟密钥版图标（形状没动）明显不一致、也跟改之前的效果不一样。

### 根因

图标源图（1024×1024）当时是"内容铺满整个画布、四周无边距"的做法，圆角半径也是早期估的约 180px，跟苹果官方 macOS 图标模板的实际规格（824×824 内容 + 四周 100px 透明边距 + 185.4px 圆角，见 `developer.apple.com` 官方 Design Resources 模板）并不一致。在没有配套补上正确边距的情况下，只是把圆角曲率往"更圆"的方向调，图标形状偏离 macOS 内部"这是不是一张已经按规范画好的图标"判断的容忍范围太多，触发了系统兜底逻辑：不信任这张图已经是正确形状，自动套一层灰框、把内容整体缩小塞进去，而不是直接使用图标本来的样子。

### 修复

按苹果官方模板重新生成主图：824×824 内容居中放进 1024×1024 画布，四周留 100px 透明边距，圆角改成官方规定的 185.4px。两个版本的图标共用同一套边距/圆角规格，只有内部颜色不同（见 `scripts/apply-apple-icon-spec.py`）。

### 防回归要求

- 改图标圆角/边距之前，先核对苹果官方 macOS 图标模板的具体数字（1024 画布 / 824 内容 / 185.4 半径 / 100px 边距），不要凭感觉估一个"看起来差不多"的值；
- 图标形状改动光看生成出来的 PNG 预览不够，必须真的在 Finder/Dock 里打开验证一次——静态预览图没问题不代表 macOS 系统合成后也没问题。

## 1.2.0：给登录版图标手绘的描边，四个圆角比四条直边细

### 现象

为了让白底的登录版图标在浅色 Dock/Finder 背景下有边界感，手动加了一圈浅灰色描边；肉眼看四个圆角处的描边明显比直边细，缩小到实际展示尺寸（比如 Dock 上的小图标）后更明显，某些尺寸下圆角处的描边直接消失不见。

### 根因

最初用 PIL 的 `ImageFilter.MinFilter`（方形结构元素）对图标的圆角蒙版做腐蚀来生成描边内圈——方形核腐蚀一条直线时，往里缩的距离正好等于核的半径；但腐蚀一段圆弧时，圆角 45° 中点方向会往里多缩进约 41%（方形结构元素的对角距离比轴向距离长 √2 倍，也就是棋盘距离和欧氏距离的差异）。圆角内圈因此变成一段粗糙的、近似八边形的曲线，不是平滑同心圆弧，这段粗糙轮廓缩小后就读成了"更细/更虚"。

换成用 `ImageDraw.rounded_rectangle` 精确画出内缩圆角矩形（半径按描边宽度等比缩小）之后，源文件本身的描边宽度经测量确认已经均匀，但最终在 Finder 里实际合成出来，四角看起来依然比四边"弱"——怀疑是跟 macOS 自己的动态阴影（官方规格是向下偏移 12px，本来就不是四面对称）叠加造成的观感差异，这部分已经超出静态文件能验证的范围。

### 修复

放弃手绘描边这个方向，改用图标背景本身的浅色渐变（顶部到底部，接近白色到浅灰色）来提供边界感，不再依赖任何形式的描边/边框。

### 防回归要求

- 给一个已经是圆角形状的图标加"均匀描边"，不要用方形腐蚀核（`MinFilter`）去算内圈——圆角处天然会腐蚀过头，改用 `ImageDraw` 直接画出目标半径的内缩形状；
- 描边/边框源文件测量均匀，不代表系统合成后视觉上也均匀——涉及会被 macOS/浏览器动态叠加阴影或缩放的图标，最终效果只能用真机截图验证，不能只信任静态像素测量；
- GitHub 渲染 README.md / docs/DEVELOPMENT.md 里的 HTML 时会剥离 `style`/`class` 属性（安全考虑），CSS 阴影或边框在这些文档页面永远不会生效——需要给文档里的图片做视觉强调，只能靠图片本身的像素，不能指望 CSS；
- 一个"描边/边框"方向反复调整多轮仍然拿不到稳定效果时，考虑换一个不依赖描边本身的方案（比如背景色渐变），不要在一个天生对渲染环境敏感的方案上无限打磨。

## 1.1.1：退出登录时中途崩溃，界面卡在导出完成状态

### 现象

点击"退出登录"后，上一次导出的任务列表和状态卡片仍然显示；"开始导出"变成可点状态，点击后先提示"登录状态已丢失，请重新登录"，界面才真正恢复成未登录状态。

### 根因

1.1.0 把"开始导出"/"在访达中显示"合并成一个按钮时，移除了 `#reveal` 这个 DOM 元素，但退出登录的处理函数里遗留了两行仍然操作 `$("reveal")` 的代码。`$("reveal")` 此时是 `null`，访问 `.hidden`/`.classList` 直接抛异常，把这个 `async` 处理函数从这一行往后的所有清理逻辑（`setAuthUI(false)`、`clearTaskList()`、隐藏状态卡片）全部中断——JS 异常没有被 try/catch 兜住，也没有任何报错提示。轮询循环因为 `loggedIn` 变量从未被真正置为 `false`，继续正常运行，用已经被重置的保存位置重新算出"开始导出"可点，制造出一种"部分恢复"的假象，直到用户点下去，靠 `zhihu_me()` 拿不到 token 这个副作用才间接触发了真正的清理。

### 修复

删除这两行引用已不存在元素的死代码。

### 防回归要求

- 删除一个 DOM 元素时，必须全文搜索它的 id，确认没有遗留引用，不能只改看得到的那几处；
- 像退出登录这种"多步清理"逻辑，中间任何一步意外抛出都不该让后面的步骤全部跳过——必要时包一层 try/catch，或者把顺序调整成"先做最关键的状态重置，再做次要的 DOM 清理"。

## 1.1.0：退出登录后，上一次导出的任务列表和"在访达中显示"按钮没有消失

### 现象

退出登录后，界面顶部正确恢复成未登录状态，但下面仍然显示上一次导出的任务列表，"在访达中显示"按钮也还在。

### 根因

两个问题叠加：退出登录的处理函数只隐藏了状态卡片，没有调用清空任务列表的函数；即使清空，1.2 秒一次的轮询循环也会立刻从后端 `/api/status` 重新拉取上一次导出的进度并重新渲染——退出登录只是 Tauri 侧清掉知乎登录会话，不经过 HTTP 请求，Node 后端内存里的导出进度状态完全不受影响，还是"上一次导出已完成"那份数据。

### 修复

补上清空任务列表的调用；新增 `POST /api/reset` 接口清空后端进度状态，退出登录时调用；轮询循环增加登录状态判断，未登录时直接跳过渲染。

### 防回归要求

- 任何"清空界面"的操作，要同时检查本地状态和轮询/远程数据源两边——只清一边，容易被下一次轮询或请求覆盖回去；
- 前后端分离的架构里，"登出"如果只发生在一侧（比如这里只发生在 Tauri 侧），另一侧的状态需要显式清理，不能假设它会自动跟着失效。

## 1.1.0-preview.1：关于面板"网站"/"源码"链接文字不可见

### 现象

"关于"面板里"网站"和"源码"两个链接按钮，文字和背景融在一起，看不见。

### 防回归要求

见下面"强调色按钮上的文字看不清"条——`AccentColor`/`AccentColorText` 这类系统颜色关键字用作文字颜色都不可靠，涉及可读性的地方一律用写死的颜色值，不要依赖系统关键字解析。

## 1.0.0-preview.6：打包应用下载后提示"已损坏"，无法打开

### 现象

从浏览器正常下载 dmg 安装后，双击应用直接提示"知档.app 已损坏，无法打开。你应该将它移到废纸篓。"，没有任何绕过方式——不是预期中可以在系统设置里手动允许的"无法验证开发者"提示。

### 根因

打包出的 `.app` 整体没有代码签名。Rust 编译器只会给主可执行文件加一个不完整的 linker 级签名（`codesign -dv` 显示 `Sealed Resources=none`），bundle 里的后端 sidecar 二进制和其他资源都没有被签名覆盖。较新版本 macOS 对完全未签名、又带着"从网络下载"隔离标记（`com.apple.quarantine`）的应用会直接判定为已损坏并拒绝打开，不再像早期版本那样退回到可绕过的"未知开发者"提示。

本地直接 `open` 打包出的 `.app` 一直能正常打开，掩盖了这个问题——本地生成的文件不带隔离标记，根本不会触发这条检查路径，只有真正从网上下载才会暴露。

### 修复

在 `tauri.conf.json` 的 `bundle.macOS.signingIdentity` 设为 `"-"`，让 `tauri build` 自动对整个 bundle（包括 sidecar）做 ad-hoc 签名，不需要 Apple 开发者账号。用手动添加 `com.apple.quarantine` 标记模拟真实下载场景验证过，确认恢复成预期的"系统设置 → 隐私与安全性 → 仍要打开"这个可绕过的两步流程。

### 防回归要求

- 每次正式发布前，必须用 `xattr -w com.apple.quarantine "0083;$(date +%s);Safari;" 知档.app` 模拟下载场景手动验证一次；只在本地 `open` 打开验证不会暴露这个问题；
- `codesign --verify --deep --strict` 必须通过，且 `Sealed Resources` 不能是 `none`。

## 1.0.0-preview.6：禁用状态的强调色按钮看起来仍像可以点击

### 现象

"开始导出"这类用强调色（`AccentColor`）填充的主按钮，disabled 时只是把不透明度降到 0.5，高饱和度的蓝色背景半透明后依然很显眼，跟灰色的次要按钮 disabled 后几乎不可见形成鲜明对比，容易让用户误以为还能点。

### 根因

`button[disabled]` 规则只处理了 `opacity`，没有覆盖背景色，导致不同 variant 的按钮 disabled 后视觉一致性缺失。

### 修复

`button[disabled]` 统一改成中性灰色背景，不管原本是主按钮还是次要按钮。

### 现象

内嵌的知乎登录窗口标题栏显示"Tauri App"，跟应用本身没有任何关系。

## 1.0.0-preview.5：应用图标在 Dock 中显示为直角方块

### 现象

Dock 里应用图标是直角正方形，不是 macOS 标准的圆角造型。

## 1.0.0-preview.5：主窗口内容出现纵向滚动条

### 现象

窗口内容比窗口本身高，出现滚动条；手动拖动窗口边缘调整大小后更容易复现。

### 根因

两个问题叠加：

1. 用 `document.body.scrollHeight` 测量内容高度来动态调整窗口大小，但 `main` 元素的 `margin-top:64px` 因为 CSS margin collapse 穿透了没有 border/padding 的 `body`，没有被 `scrollHeight` 计入，导致算出的目标高度总是偏小；
2. 窗口本身允许用户手动拖拽调整大小；如果拖得比内容矮，跟"窗口大小完全由内容驱动"这个设计前提直接冲突，必然产生滚动条。

### 修复

- 改用最后一个元素（`footer`）的 `getBoundingClientRect().bottom` 测量真实渲染高度，不受 margin collapse 影响；resize 后还会二次检测是否仍有溢出并自动补足，不完全依赖一次性算准；
- 把主窗口设为不可手动调整大小（`resizable:false`）——窗口高度既然完全由内容驱动，允许用户拖拽只会重新引入这个问题。

### 防回归要求

- 不要用 `document.body.scrollHeight` 测量整页高度，除非确认根节点到 `body` 之间没有会发生 margin collapse 的外边距。

## 1.0.0-preview.4/preview.5 之间：强调色按钮上的文字看不清

### 现象

蓝色（`AccentColor`）按钮上的文字是黑色，跟背景对比度很差。

### 根因

`color:AccentColorText` 这个 CSS 系统颜色关键字在当前使用的 WKWebView 版本里没有解析出可读的文字颜色，回退成了黑色而不是预期的白色。

### 修复

不依赖 `AccentColorText`，直接写死 `color:#fff`。

## 0.3.3：残留Chrome进程导致登录窗口无法再次打开

### 现象

```text
无法打开登录窗口：browserType.launchPersistentContext: Target page, context or browser has been closed
```

Chrome启动日志中可见"正在现有的浏览器会话中打开。"

### 根因

服务被强制终止（例如直接`kill`进程，而不是通过`/api/close`）时，Playwright启动的独立Chrome进程不会跟着一起退出，成为孤儿进程，继续占用`.data/browser-profile`。下次启动服务后再次点击登录，新Chrome进程发现Profile已被占用，转发给旧进程后立即退出，导致Playwright连接失败。

### 修复

- 监听`SIGINT`和`SIGTERM`，收到后先调用`client.close()`优雅关闭浏览器，再退出进程。

### 防回归要求

- 正常方式（Ctrl+C、非`-9`的`kill`）停止服务时，浏览器进程必须一并退出；
- 不得假设进程被终止后浏览器会自动清理；`kill -9`强杀属于已知例外，任何架构都无法覆盖。

## 0.3.3：登录浏览器提示不受支持的命令行标记

### 现象

Chrome信息栏提示"您使用的是不受支持的命令行标记：--no-sandbox。稳定性和安全性会有所下降。"

### 根因

Playwright的`chromiumSandbox`选项默认值是`false`，因此每次启动都会自动加上`--no-sandbox`，与是否root或使用的平台无关；项目代码此前没有显式设置这个选项。

### 修复

- 在`launchPersistentContext`中显式设置`chromiumSandbox:true`，恢复Chromium的沙盒隔离。

### 防回归要求

- 修改浏览器启动参数时，需要确认沙盒仍然开启（启动命令中不应包含`--no-sandbox`）。

## 0.3.1：浏览器关闭后无法再次登录

### 现象

点击“打开登录窗口”后出现：

```text
无法打开登录窗口：page.goto: Target page, context or browser has been closed
```

### 根因

独立Chrome窗口被关闭后，服务器仍保留旧的Playwright `BrowserContext`和`Page`引用。再次登录时，旧代码只检查上下文变量是否存在，没有确认页面和浏览器是否仍然有效。

测试过程中还发现，4317端口上的旧服务器进程会继续提供旧版代码，使已经修复的源码看起来仍然报同样错误。

### 修复

- 监听页面和浏览器上下文关闭；
- 自动清除失效引用；
- 页面关闭但上下文有效时创建新页面；
- 导航遇到目标已关闭时重建上下文并重试一次；
- 关闭失效上下文时忽略“已经关闭”的清理错误；
- 文档增加端口、旧进程和旧构建检查方法。

### 防回归要求

- 不得假定非空对象就是有效浏览器对象；
- `/api/status`不得为了检测登录状态反复创建或访问页面；
- 修改浏览器生命周期后要测试“打开、手动关闭、重新打开、服务端关闭”四种路径。

## 0.3.1：120条被误判为只取得119条

### 现象

```text
知乎返回总数120，实际取得119，为避免生成不完整归档已停止。
```

### 根因

旧代码把接口报告的原始分页总数与去重后的唯一内容数量直接比较。分页边界、置顶内容或接口行为可能让同一个ID出现两次。例如接口实际返回120条记录，其中一条重复，正确结果应是119篇唯一内容，而不是漏掉一篇。

### 修复

分页报告现在分别保存：

```json
{
  "reportedTotal": 120,
  "received": 120,
  "unique": 119,
  "duplicates": 1,
  "warning": null
}
```

- `reportedTotal`：接口声称的记录数；
- `received`：所有分页原始返回记录数；
- `unique`：按内容类型和ID去重后的数量；
- `duplicates`：重复记录数；
- `warning`：原始返回数与接口总数不一致时的警告。

只有`received`与`reportedTotal`不一致才产生完整性警告。工具仍导出能够取得的内容，并把警告写入`export-report.json`，不再因为可解释的重复记录而停止。

### 防回归要求

- 完整性检查必须发生在去重前；
- 去重不能静默进行，必须报告重复数量；
- 不得把接口总数、原始记录数和唯一内容数混成一个字段。

## 0.3.0：状态轮询产生高频外部请求

### 现象

页面只是保持打开，也会频繁请求账号接口，增加限流和安全验证概率。

### 根因

前端每1.2秒调用本地`/api/status`，旧服务器每次收到状态请求又调用一次第三方`/api/v4/me`。

### 修复

登录状态保存在本地进程内存。`/api/status`只返回本地状态，只有用户确认登录和开始导出时才检查实际账号会话。

## 0.3.0：图片重复

### 现象

Markdown或网站中同一张正文图片连续出现两次。

### 根因

懒加载页面可能同时包含正常`img`节点和`noscript`备用图片；二者转换成Markdown后成为两张相同图片。

### 修复

- 优先使用`data-original`和`data-actualsrc`；
- 删除`noscript`备用块；
- 按图片内容SHA-256命名和去重；
- 增加重复懒加载图片测试。

## 0.3.0：图片失败被静默忽略

### 现象

图片没有下载到本地，但导出过程仍显示成功，之后使用归档时才发现缺图。

### 根因

旧代码使用空的`catch {}`吞掉所有图片下载异常。

### 修复

- 每张图片最多尝试三次；
- 下载失败时保留远程地址；
- 把内容ID、图片地址和错误写入`export-report.json`；
- 不再把部分成功伪装成完整成功。

## 0.3.0：没有封面、问题ID和收藏数

### 现象

网站无法可靠显示封面，回答无法直接取得问题ID，收藏排序没有数据。

### 根因

初始导出格式没有请求或保存这些字段。

### 修复

- 回答保存独立`questionId`；
- 请求可用的`image_url`或`thumbnail`；
- 没有封面字段时使用正文第一张有效图片；
- 请求可用的收藏字段；接口不提供时保存`null`，不伪造为零。

## 0.3.0：可能覆盖已有归档

### 现象

用户选择已有目录时，索引、报告或同名文件可能被覆盖。

### 根因

初始版本直接在用户输入路径中创建和写入文件，没有验证目录是否为空或是否属于受保护位置。

### 修复

- 只允许不存在或为空的导出目录；
- 拒绝磁盘根目录、用户主目录、项目根目录和内部数据目录；
- 完整导出与未来的增量更新明确分离。

## 0.2.0：登录页或安全验证页被当作JSON

### 现象

登录失效或触发安全验证后出现不清楚的JSON解析错误。

### 根因

旧实现假定成功响应一定是内容JSON，没有先检查HTTP状态、Content-Type和HTML响应。

### 修复

- 检查401、403和其他HTTP状态；
- 检查`Content-Type`；
- 检测HTML登录或安全验证页面；
- 返回明确提示，让用户在正常Chrome窗口中完成验证；
- 不绕过验证。

## 历史日志中的无关页面错误

早期页面环境中出现过第三方监控脚本或页面`fetch`失败。这类错误不一定意味着文章下载失败。当前内容请求通过Playwright浏览器上下文直接发出，不依赖知乎页面中的脚本环境；只有内容接口、图片请求或导出报告明确记录的失败才计入归档失败。
